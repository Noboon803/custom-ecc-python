# コメントと docstring

コメントの読み手は「半年後にこのコードを初めて読む人」とする。今の会話の相手やレビュー担当者に向けて書かない。コードを読めばわかることは書かず、コードからは読み取れないことだけを書く。

## 書くもの

- 公開しているモジュール・クラス・関数・メソッドの docstring（PEP 257）。非公開（`_` 始まり）のものは、処理が自明でない場合だけ書く
- コードから読み取れない「なぜ」: 外部の制約、不具合の回避策、意図的に一般的でない書き方をした理由。関連する Issue や資料があれば URL を添える
- `# noqa` / `# type: ignore` で警告を抑えるときは、その理由（例: `# noqa: T201 - CLI の標準出力`）

## 書かないもの

- コードの読み上げ（例: `# ユーザーを取得する`、`# ループで合計する`）
- 変更履歴や作業報告（例: `# バグを修正`、`# 新しく追加`、`# 〜から変更`）。これらはコミットメッセージや PR に書く
- 会話相手に向けた言葉（例: `# ご要望どおり〜にしました`）
- 型ヒント・関数名・変数名を見ればわかること
- コメントアウトしたコード。不要なら消す（履歴は Git に残る）
- `# ----` などの区切り線や見出しコメント。区切りが必要なほど長いなら、モジュールを分ける
- 要求元の資料の情報（セクション名やタスク名等）

## 書き方

- 日本語で書く。docstring の 1 行目は「何をするか」を 1 文で書く
- コメントを書きたくなったら、先に名前の変更・関数の抽出・型ヒントで表せないか検討する
- コードを変更したら、関係するコメントも同じ変更の中で直す。コードと食い違うコメントは、ないより悪い（PEP 8）
