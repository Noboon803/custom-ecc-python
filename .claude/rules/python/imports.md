# import

## 位置

import はモジュールの先頭（モジュールの docstring の直後）にまとめて書く。関数・メソッド・クラスの中には書かない（PEP 8）。ruff の `PLC0415` で検出される。

先頭にまとめる理由: モジュールが何に依存しているかが一目でわかり、import の誤りがその関数を呼んだときではなくモジュールを読み込んだ時点で見つかる。

### 例外

次の場合だけ、関数内の import を認める。その際は `# noqa: PLC0415 - <理由>` で理由を書く。

- 循環 import を避ける必要があり、モジュールの分け方では解消できない
- 読み込みが重い、または一部の環境にしかない任意の依存で、使う箇所でだけ読み込みたい

型ヒントのためだけに必要な import は、関数内ではなく、モジュールの先頭の `if TYPE_CHECKING:` ブロックに書く。

`# noqa` で済ませる前に、まず import を先頭に移せないか、モジュールの分け方で循環を解消できないかを検討する。

## import する単位

- 同じパッケージの中では、定義しているファイル（モジュール）から直接 import する。パッケージの `__init__.py` を経由しない
- パッケージの外から使うものは、そのパッケージの `__init__.py` で再エクスポートした公開 API を、パッケージから import する
- 同じモジュールから import する名前が多く import 文が長くなる場合は、名前ではなくモジュールを import し、使う側でモジュール名を付ける

```python
# 名前を個別に import すると長くなる場合
from myapp.billing.invoice import Invoice, InvoiceLine, InvoiceStatus, create, cancel

# モジュールを import する
from myapp.billing import invoice

invoice.create(...)
```

### `__init__.py` での再エクスポート

- パッケージの外に公開するものだけを再エクスポートし、`__all__` に列挙する
- パッケージ内部でしか使わないものまで再エクスポートしない。循環 import が起きやすくなり、使うたびにパッケージ全体が読み込まれ、定義の場所も import 文から読み取れなくなる

## 補足

import の行が多いこと自体は問題ではない（並び順は ruff の `I` が整える）。1 つのファイルが多くのモジュールに依存しているなら、そのファイルが役割を抱えすぎていないか見直す。
